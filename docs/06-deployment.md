# 06 · 部署与运维设计

> 版本：v1.1（待实现、待演练）
> 更新日期：2026-10-02
> 实施状态（2026-10-02）：M0 基础工程已落地，实际版本、命令、接口与验证见 [09 · 底座使用与验收](09-foundation.md)。本文尚未标注实现的业务能力仍为设计。

## 1. 部署基线与前提

首版采用受维护的 Linux 发行版、Docker Engine 与 Compose v2，单机试点。建议以 8 vCPU / 16 GiB / SSD 作为联调和压测参考，最终配置取决于实测容量、附件增长和备份空间。生产系统、数据库、Redis、对象存储、Nginx 和 Java/Node 版本在 M0 锁定；不使用 `latest`，不继续推荐 CentOS 7 或无维护支持的工具链。

单机方案有主机故障单点，自动重启和主从复制不能单独构成高可用。首版恢复目标为 RPO ≤ 24 小时、RTO ≤ 4 小时，月可用性目标 99.5%；均须由演练验证。

## 2. M0 必须交付的文件

下表为生产交付目标；已实现文件与实际路径以 09 文档为准。

| 计划文件 | 内容与验收 |
|---|---|
| deploy/compose.yaml | 固定镜像引用、私有网络、数据卷、健康检查、日志轮转、重启策略 |
| deploy/.env.example | 非敏感配置和必填变量说明；没有可登录的默认密码 |
| deploy/secrets/ | 仅部署主机持有的密码/密钥文件，限制读取权限，不入版本库 |
| deploy/nginx/nginx.conf | HTTPS、SPA、API、WebSocket、上传限制与访问日志 |
| deploy/mysql/my.cnf | 字符集、UTC、持久化、binlog 与容量配置 |
| deploy/redis/redis.conf | ACL/密码实际注入方式、持久化、noeviction 与内存限制 |
| 后端版本化迁移目录 | 底座初始化、业务表、字典和升级脚本；空库与旧库升级验证 |
| deploy/backup/ | 一致性备份、校验、异机复制、隔离恢复和过期清理脚本 |
| deploy/releases/ | 每次发布的镜像摘要、配置版本、迁移版本和回滚说明 |
| CI 配置 | 测试、构建、迁移验证、镜像发布和可追溯版本记录 |

生产与演示数据分开，禁止自动创建公共 admin/demo 密码。首次管理员通过一次性初始化流程创建并强制更改凭据。运行应用使用最小权限数据库账号；迁移账号和备份账号独立。

## 3. 构建与配置契约

后端构建必须执行测试，前端使用锁文件冻结依赖，镜像使用构建提交标识和摘要。具体构建命令、JAR 名称、前端脚本名与端口，待选定底座后从真实构建验证结果填写，不能预设 `agentoa-admin-1.0.0.jar` 一定存在。

Compose 发布镜像建议采用如下**配置片段**，不是完整服务定义：

```yaml
services:
  backend:
    image: ${AGENTOA_BACKEND_IMAGE:?set immutable backend image reference}
    restart: unless-stopped
  web:
    image: ${AGENTOA_WEB_IMAGE:?set immutable web image reference}
    restart: unless-stopped
```

发布变量直接引用完整镜像（推荐带 sha256 摘要），回滚时恢复同一组前后端引用。不要修改未被 Compose 使用的 TAG 变量。Compose `.env` 只用于插值，不会自动导出给宿主机脚本或写入 Redis 配置。

| 配置 | 要求 |
|---|---|
| 数据库 | 使用容器服务名，设置 UTC；明确 JDBC 与底座数据源配置项的映射 |
| Redis | 明确客户端密码/ACL 与服务端实际读取值一致；redis.conf 不会自动展开环境变量 |
| 对象存储 | 应用用限定桶权限的服务账号；禁止使用对象存储 root 凭据 |
| 会话 | Sa-Token 不透明令牌，不需要 JWT_SECRET；有效期与 API 文档一致 |
| 加密 | 字段加密和 HMAC 密钥分开，记录密钥版本和恢复方式 |
| JVM | 容器内存、堆与非堆预算协调；JAVA_OPTS 必须由入口脚本明确消费 |
| 上传 | 单文件 20 MiB；应用限制文件大小，Nginx 请求体上限 21 MiB 留出 multipart 开销 |
| 文件地址 | 首版应用鉴权后代理下载，客户端不接收对象存储容器内部地址 |

禁止把生产 `docker compose config` 展开结果上传到日志或工单；配置校验使用静默模式，凭据从受控文件/密钥服务读取。Compose 本地 secrets 是文件挂载机制，不应误称为加密密钥服务。

## 4. 网络、存储与健康检查

| 服务 | 暴露范围 | 就绪条件 |
|---|---|---|
| Nginx | 对用户开放 443，80 仅重定向或证书挑战 | 配置检查通过，证书链与静态资源可用 |
| 后端 | 仅容器网络；运维调试可临时回环绑定 | 数据库迁移完成，依赖和核心业务探测正常 |
| MySQL | 容器网络或受控运维入口 | 认证查询成功，目标 schema/迁移版本正确 |
| Redis | 容器网络 | 带应用凭据 PING 成功 |
| 对象存储 | 容器网络；控制台仅受控管理入口 | 健康检查、桶存在、服务账号读写测试通过 |
| 指标/日志 | 运维网络 | Prometheus 可抓取，告警链路实际验证 |

`depends_on` 的启动顺序不等于服务就绪。实现健康检查后使用 `condition: service_healthy`，迁移作为一次性任务成功后再启动应用，应用还需有限重试。健康探针命令必须确认镜像内存在所需工具。

MySQL 建议 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、UTC 会话与 `utf8mb4`。binlog 保留时长需覆盖已验证的备份周期；禁止用降低持久性来掩盖未经压测的性能问题。

Redis 保存会话时采用 `noeviction` 并监控内存，或将会话与可丢弃缓存拆实例。对象桶保持私有，持久卷、所有者权限、磁盘余量和日志轮转全部进入启动验收。备份放在异机或独立故障域，不能只放同一主机的数据盘。

## 5. Nginx 与证书约定

| 路由 | 行为 |
|---|---|
| / | SPA 静态资源；index.html 不长期缓存，带哈希资源可长期缓存 |
| /api/v1/ | 原路径代理到后端；保留 Authorization，传递请求 ID |
| /ws | WebSocket Upgrade、HTTP/1.1、心跳和空闲超时协调 |
| /actuator/、/v3/api-docs、/swagger-ui/ | 公网禁止；仅受控运维/测试访问 |

后端仅信任来自既定代理的转发头。API 使用前缀优先匹配，避免静态资源扩展名规则截获接口；设置 `client_max_body_size 21m`，限流返回 429，办公网共用出口时避免低额度 IP 限流阻断全体员工。

访问日志记录路径而不记录查询参数、Authorization 或 ticket；WebSocket 同时校验 Origin，服务端将 ticket 原子消费一次。不要将 S3 签名请求随意挂到重写路径的 `/minio/` 代理，签名的 Host/path 变化会导致失败。

证书初次申请必须在 HTTPS 服务启动前完成。选择 webroot 或 DNS challenge，避免 standalone 与已占用的 80 端口冲突。续期要更新 Nginx **实际读取的文件**，若使用复制目录需部署钩子原子替换证书，再执行配置检查和 reload；只续期源文件并重启容器不会更新旧副本。上线前演练一次续期，配置到期告警。

## 6. 首次部署验收顺序

在 M0 文件交付后，所有 Compose 命令统一从项目根目录调用同一文件及环境配置。以下仅是命令格式示例，当前不能运行：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml pull
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
```

执行前依次完成：版本和凭据检查 → TLS 与数据目录准备 → 基础服务就绪 → 迁移任务 → 私有桶和服务账号初始化 → 应用/Web 启动 → 核心业务验收。迁移工具、初始化任务和健康检查未交付时不得宣称上述命令可一键部署。

验收包含：登录与退出、角色越权拒绝、完整请假审批、重复提交、文件上传下载、WebSocket 断线补拉、容器重启后数据仍在。检查数据库与控制台端口未向用户网段暴露。

## 7. 备份与恢复

### 7.1 一致性备份

首版采用每日维护窗口备份，先禁止新写入并等待在途事务结束，暂停后台消费者/调度/上传，随后备份 MySQL、对象文件及配置，再恢复业务。这是小规模试点的建议实现；若无法接受每日短暂停写，必须另行验证在线一致性备份方案。

备份脚本需具备：

- Bash `set -euo pipefail`，确保 mysqldump 失败不会被 gzip 成功掩盖。
- 独立备份账号和受控客户端配置文件，不在命令行拼接明文密码，不假设 cron 会继承 Compose 环境。
- 数据库一致性导出、对象版本/清单和校验和；不能直接 tar 正在写入的对象存储目录并声称可恢复。
- 临时文件写入、完整性校验、原子更名、异机复制验证后才标记成功；错误时告警并恢复暂停的服务。
- 记录统一备份 ID、时间点、镜像/迁移版本、对象数量、哈希及加密密钥版本。密钥单独保管。
- 默认保留 30 天，过期清理限制在明确的备份目录和命名范围，确认存在较新的有效异机备份后才清理。

仅开启 binlog 不代表已实现增量恢复；更短 RPO 需补充 binlog 连续归档、位置记录和时间点恢复演练。

### 7.2 恢复演练

1. 在隔离环境准备与备份兼容的镜像、数据库版本和空数据卷。
2. 校验备份与校验和，恢复数据库、对象文件、配置和对应加密密钥。
3. 校验 schema 版本、账号/流程/报销记录数量、附件引用和文件可读性。
4. 默认撤销原会话，避免恢复旧 Redis 状态导致已注销或已离职会话重新有效。
5. 启动应用，验证登录、历史审批、余额、付款记录与附件；恢复/去重 outbox。
6. 记录实际数据丢失窗口、恢复耗时、失败项和负责人，达到 RPO/RTO 才能发布。

生产恢复需进入维护窗口并保留当前数据快照，不覆盖运行中的数据卷。每月至少演练一次，关键数据库或存储升级后追加演练。

## 8. 监控与故障排查

| 现象/指标 | 首先检查 |
|---|---|
| 登录失败或大面积 401 | 会话过期、账号状态、Redis 认证/容量、权限缓存；不检查不存在的 JWT Secret |
| 审批卡住/通知延迟 | 引擎任务状态、业务事务失败、outbox 积压与重试错误 |
| 附件上传/下载失败 | 应用授权、请求体限制、桶权限、磁盘与对象完整性 |
| WebSocket 断开 | ticket 有效期与单次消费、Origin、Upgrade、超时、重连补拉 |
| 5xx / 延迟升高 | 近 5 分钟错误率、p95、线程池/连接池、慢 SQL、CPU/内存 |
| 备份超时或失败 | 最近成功备份时间、异机校验、可恢复性，不能只看文件存在 |
| 证书或磁盘风险 | 证书剩余 < 14 天、磁盘 > 80% 提醒，> 90% 升级 |

告警渠道、接收人和维护窗口由部署方配置并测试。应用探针至少连续两次失败告警，outbox 延迟和备份过期应有业务告警。监控组件也需固定镜像与权限；不部署未配置数据源的空看板。

## 9. 发布与回滚

单实例 Compose 首版采用**维护窗口内替换发布**，不宣称滚动/蓝绿或零停机。

1. 记录当前前后端镜像摘要、配置与迁移版本，核验新版本测试和迁移结果。
2. 完成备份并确认可恢复；开启维护模式、停止写入和后台任务。
3. 执行兼容迁移，更新 Compose 真正引用的前后端镜像变量。
4. 重建服务，轮询就绪探针至明确截止时间，再执行登录、审批、消息与文件冒烟测试。
5. 失败时保留日志；若数据库仍向后兼容，恢复上一组镜像和配置并重新验收。
6. 不兼容迁移不能只回滚镜像：选择修复前进或经核对恢复备份，并明确恢复点之后的数据处理。
7. 成功后关闭维护模式，恢复调度，观察错误率和积压，记录发布结果。

先扩展再收缩数据库结构，避免同一次发布立即删除旧列。后续若确有零停机需求，另行设计双环境、流量切换、连接排空和共享数据库兼容性。

## 10. 上线门槛

- [ ] 在干净 Linux 主机上按真实文件完成部署和重启验证。
- [ ] 镜像、构建、迁移和配置均可追溯，无公共默认凭据。
- [ ] 核心业务和越权测试、压测通过。
- [ ] 数据库、附件、密钥和配置恢复演练达标。
- [ ] 证书续期、告警、失败发布与回滚经过演练。
- [ ] 运维负责人、备份留存和故障处理流程明确。
