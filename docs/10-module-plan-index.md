## 使用方式

每个模块文档都是一个可独立评审的开发包。评审时先确认范围、字段、状态和验收场景，再进入实现；确认后的变更要同时更新需求、迁移、API 和本模块计划。文档中的 P0 是 v1.0 必须能力，P1 留到 P0 稳定后实施；已交付的 P1 批次一见 09 第 15 节，其余 P1 另行排期。

所有模块沿用 M0 约束：单组织、Spring 事务、Flowable 7.2.0、MySQL 8.4、Redis 会话、S3 私有文件、outbox 通知、不透明 Bearer 会话。业务表使用 V4 及后续 Flyway 迁移，不能修改已执行的 V1–V3。

## 每个模块的统一完成定义

模块必须同时具备：版本化迁移、后端领域服务、权限矩阵、API 契约、前端页面、异常和幂等处理、审计字段、自动化测试、验收数据和文档更新。页面能打开或接口能返回不算完成。

每个模块至少提供以下证据：

1. 空库迁移与已有数据升级各执行一次。
2. 正常流程、重复提交、并发冲突、越权访问和事务回滚测试。
3. 角色矩阵测试：普通员工、直属主管、HR、财务、管理员至少覆盖本模块主要动作。
4. 关键列表、详情、导出和文件下载的对象权限测试。
5. 前端生产构建和浏览器主流程回归。

## 建议迭代节奏

每个模块先做契约和迁移，再做服务与 Flowable 适配，最后做页面和联调。每个模块拆成 1 个准备迭代、2–3 个开发迭代和 1 个验收迭代；只有验收通过才进入下一个模块。跨模块需求进入依赖模块的变更清单，禁止在后续模块中偷偷扩展前置模块的数据语义。
